# Компоненты и когда каждый уместен

Главное правило, из которого следуют все остальные: **структурный приём обязан кодировать
правду о содержании, а не украшать.** Нумерация — только если есть порядок. Дорожка — только
если есть владелец. Цвет участника — только если участников больше одного. Иначе это шум.

## Каталог

| Компонент | Разметка | Когда уместен |
|---|---|---|
| masthead | `header` + `.eyebrow` + `h1` + `.standfirst` | всегда; героя во весь экран не делать |
| readout | `.readout` + `.cell` (`.hot` для сигнальной) | 2–6 ключевых величин, которые читатель должен унести |
| раздел | `section` + `.sec-head` + `.rank` + `h2` | `.rank` только когда разделы правда упорядочены |
| фигура | `figure` + `.fig-head` + `.fig-body` + `figcaption` | обёртка любой схемы, диаграммы, графика |
| легенда | `.legend` + `.sw` | как только на схеме больше одного цвета |
| таблица | `.tw` + `table`, `td.n` для чисел | плотные факты: маппинги, константы, матрицы |
| врезка | `.note`, `.note.warn`, `.note.ok` | тонкость, ловушка, следствие |
| метка | `.tag.sig` / `.tag.line` / `.tag.ok` / `.tag.warn` | статусы, состояния, сила рекомендации |
| терминал | `.term` + `.g .y .r .d .c` | дословный вывод команды или статусной строки |
| проза | `p` (узкая), `p.wide`, `ul.tight` | по умолчанию узкая колонка `--measure` |

## Схема: mermaid или руками

**Mermaid — когда связи графовые.** Поток данных, зависимости модулей, вызовы, машина
состояний, последовательность во времени. Раскладку считает библиотека, и это единственная
причина её тащить: дописать ребро дешевле, чем перерисовать.

```
flowchart LR    — поток, зависимости
sequenceDiagram — обмен во времени между участниками
stateDiagram-v2 — состояния и переходы
erDiagram       — сущности и связи
```

**Руками — когда картинка редакторская.** Диаграмма масс (интерфейс против реализации),
разрез слоёв, шкала, «до / после», схлопывание. Mermaid этого не умеет и не должен: берите
`div` с токенами или инлайновый SVG.

Смешивать в одной странице нормально. Не нормально — рисовать графовую схему руками
и редакторскую через mermaid.

**Единственное законное исключение из «цвет только через токены».** `classDef` внутри
mermaid не понимает `var(--s1)` — там придётся написать шестнадцатеричный литерал.
Брать **ровно то же значение**, что стоит в слоте, и держать рядом:

```
classDef flow fill:#3B82C4,stroke:#3B82C4,color:#fff   /* = --s1 */
```

## Правила фигуры

- **Схема — центр, а не иллюстрация к тексту.** Проблема и вывод — по одному предложению.
- **Если схему нельзя понять без абзаца пояснений — перерисовать схему**, а не дописать абзац.
- **Подпись говорит то, чего на картинке не видно.** Пересказ схемы в `figcaption` — удалить.
- **«До / после» — рядом, а не последовательно.** Асимметрия видна только при сравнении.
- Пункты выгод — не длиннее шести слов.
- **Легенда обязательна**, как только цветов больше одного, и живёт в шапке страницы или фигуры.

## Запрет на похвалу вне словаря

Нельзя писать «стало чище», «легче поддерживать», «более гибко». Эти слова ничего не значат
и ничем не проверяются. Разрешён только словарь предметной области из `AGENTS.md` и `CONTEXT`
проекта, плюс измеримое: количество, время, число вызовов, размер диффа.

## Цвет

- **Система задаёт нейтрали, семантику и типографику. Предметные цвета — за страницей.**
  Слоты `--s1 --s2 --s3` переопределяются в `<style>` страницы под её участников.
- `--sig` — сигнал, то ради чего страница написана. Не раскрашивать им всё подряд.
- Семантика (`--warn`, `--ok`) — это **не** акцент. Роли разные, смешивать нельзя.
- Обе темы проверять глазами. Тёмная — не инверсия светлой: контраст текста и заливок
  ведёт себя иначе, а `--sig` в тёмной специально светлее.
