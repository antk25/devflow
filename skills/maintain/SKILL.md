# /maintain — регламентный проход

Чеклист, не инструмент: своих проверок у скилла нет, он вызывает чужие по порядку и заставляет
закрыть каждый пункт исходом. Итог — одна заметка `<vault>/notes/maintain-<YYYY-MM-DD>.md`.

**Исходы пункта** (ровно один на пункт):
- **PR** — мелкая механическая правка: ветка `maintain-<YYYY-MM-DD>` от базовой, коммит по формату
  `AGENTS.md`, `gh pr create` в базовую ветку; в заметку — ссылка.
- **ТЗ** — крупное: после согласия пользователя черновик `<vault>/tz/<KEY>-<slug>.md` по образцу
  соседних (frontmatter `type: tz`, `status: draft`); в заметку — путь.
- **к тикету** — крупное, но без черновика: строка в заметке. Jira не трогать; напомнить, что
  тикет заводится вручную через `/jira-create`.
- **чисто** — находок нет.
- **пропущено: <причина>** — команда недоступна или пользователь отказался; рядом строка для
  ручного запуска.

## Шаг 1. Подготовка

1. `AGENTS.md` в cwd → `project`, `vault`, базовая ветка, формат коммита. Период — аргумент,
   без него `week`; `--since` для month — `1 month ago`.
2. Диапазон и «горячие» каталоги:
   ```bash
   git log --since="1 week ago" --format=%h --reverse | head -1     # first → диапазон <first>^..HEAD
   git log --since="1 week ago" --name-only --format= | xargs -n1 dirname | sort | uniq -c | sort -rn | head -5
   ```
   Коммитов нет → заметка с одной строкой «изменений за период нет», шаги 2–3 пропускаются,
   месячные пункты шага 4 идут всё равно.
3. Проверить, нет ли уже заметки за сегодня — тогда дописывать в неё, не создавать вторую.
4. `git rev-parse --verify -q origin/HEAD` пусто → `git remote set-head origin -a`: без него
   `/security-review` падает на `origin/HEAD...`.
5. Неделя имеет смысл только в проекте с потоком коммитов; меньше 3 коммитов за период —
   предложить пропустить недельные пункты.

Проход резать на две сессии: пункты 1–2 и 4, затем `/cut` и пункт 3 (`/simplify`) — один
недельный проход целиком съедает контекст до ~130K.

## Шаг 2. Недельные пункты

Каждый пункт — отдельный вызов через `Skill`; вывод сводится до списка находок, не копируется.
Если `Skill` не находит команду — исход «пропущено: команда недоступна», в заметке строка
«запустить вручную: `/<команда> …`».

| # | Пункт | Вызов |
|---|-------|-------|
| 1 | Ревью: ось стандартов по диапазону, ось соответствия — по слагам задач периода | `/review <first>^..HEAD`; соответствие — `/review <slug>` для каждой задачи из коммитов периода, без задач — не гонять |
| 2 | Сводный code review | `/code-review` по горячим каталогам или по задачам: на всём диапазоне (десятки коммитов) diff обрезается на ~60 КБ |
| 3 | Упрощение по горячим каталогам | `/simplify` на каждом из топ-5 каталогов (по одному) |
| 4 | Безопасность | `/security-review` |

После каждого вызова: находки разобрать по исходам из шапки. Одна находка — один исход; мелкие
механические правки одного пункта идут одним коммитом в `maintain-<date>`. Перед тем как резать
PR: `git status` чистый, ветка от базовой, не от текущей feature-ветки.

## Шаг 3. Заметка (неделя)

`<vault>/notes/maintain-<YYYY-MM-DD>.md`:

```markdown
---
created: YYYY-MM-DD
project: <project>
type: maintain
period: week|month
range: <first>^..HEAD
tags: [maintain, <project>]
---

# Проход <week|month> — <YYYY-MM-DD>

Коммитов за период: N. Горячие каталоги: `a/`, `b/`, `c/`.

| Пункт | Исход | Ссылка / причина |
|-------|-------|------------------|
| /review | PR | <url> |
| /code-review | чисто | |
| /simplify a/ | к тикету | <одна строка про находку> |
| /security-review | пропущено | команда недоступна; вручную: `/security-review` |

## К тикету
- <находка> — почему не PR
```

Строка «К тикету» дублирует таблицу осознанно: её читает следующий проход, чтобы не предлагать то
же самое.

## Шаг 4. Месячные пункты

Только для `month`, после недельных. Пункты 5–7 глобальные (установка и Claude Code целиком) —
только при запуске из devflow; в остальных проектах их нет в таблице. Добавить в таблицу:

| # | Пункт | Как |
|---|-------|-----|
| 5 | Установка | `./install.sh --check` — вывод целиком в заметку под таблицей; `MISS`/`STALE` → PR или «к тикету» |
| 6 | Диагностика Claude Code | ручной: попросить пользователя запустить `/doctor` и вставить итог; без ответа — «пропущено: ждёт пользователя» |
| 7 | Разрешения | ручной: `/fewer-permission-prompts`; команды нет в установке → «пропущено: команда отсутствует» |
| 8 | Вычитка правил | `AGENTS.md` и `agents/*.md`: ссылки на несуществующие файлы и скиллы (`ls skills/`, `ls ~/.claude/skills/`), команды, которых нет в `Run`, расхождения с таблицей скиллов README; каждая — PR |
| 9 | Память проекта | `~/.claude/projects/<cwd>/memory/MEMORY.md` (в `<cwd>` каждый `/` заменён на `-`) и связанные файлы: записи «в процессе»/«не запушено» по веткам, которых уже нет (`git branch --merged main`, `gh pr list --state merged`), ссылки на несуществующие файлы, задачи со слитым PR старше месяца. **Только список на удаление в заметку** — не удалять, даже по просьбе в той же сессии: пользователь удаляет сам |
| 10 | Наблюдения | `ls <vault>/notes/*-observations.md`, вычесть упомянутые в прошлых `notes/maintain-*.md`; каждый оставшийся файл — прочитать, по каждому пункту ТЗ / к тикету / «устарело» |

Пункт 9 читает только память проекта из cwd: память других проектов проход не трогает.

## Шаг 5. Итог

Показать пользователю таблицу из заметки и список открытых PR. Проверить, что у каждого пункта
есть исход — пустая ячейка «Исход» означает незавершённый проход, заметку в таком виде не оставлять.

## Чего не делать

- Не коммитить в базовую ветку и не сливать PR — только `maintain-<date>` и `gh pr create`.
- Не запускать `/jira-create` и не писать в Jira: тикет — решение пользователя.
- Не удалять записи памяти и файлы наблюдений: только список.
- Не чинить находки `/review`, `/code-review`, `/simplify` сверх механических правок — всё, что
  требует решения о дизайне, уходит в ТЗ или «к тикету».
- Не ставить расписание: ни хука, ни таймера — запуск только руками.
