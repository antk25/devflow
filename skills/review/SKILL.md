# /review — ревью в две оси

Один прогон, два подагента, два раздела в выводе. Оси не смешиваются: у каждой свой контекст, свой
список находок и свой худший пункт. Общего «главного замечания» здесь нет — оно всегда пряталось бы
за той осью, что громче.

Отличие от соседей: `/code-review` даёт один сводный список, `/xreview` — взгляд другой модели.
Этот скилл отвечает на два разных вопроса по отдельности: «написано ли это по правилам» и
«то ли это, что просили».

## Step 1: Контекст и цель
1. Читай `AGENTS.md` из cwd → `project`, `vault`, `Branch base`, конвенции.
2. Определи, что смотреть:
   - аргумент `--uncommitted` → незакоммиченные правки;
   - SHA → `git show <sha>`; диапазон → `git diff <range>`;
   - `--uncommitted` включает staged, unstaged и untracked: `git diff HEAD` и чтение новых файлов;
   - аргумент похож на слаг → ветка задачи против базы;
   - без аргумента → текущая ветка против базы (`git diff <base>...HEAD`). База локальная —
     `git fetch` заблокирован.
3. Выведи слаг: из аргумента, иначе из имени ветки. Слаг нужен второй оси.

## Step 2: Запустить обе оси независимо
Зафиксируй cwd, базу, HEAD, слаг и точную цель до запуска. Для ветки используй
`git diff <base>...<branch>`; неизвестную базу или неоднозначный аргумент уточни, не угадывай.

| Хост | Запуск |
|---|---|
| Claude Code | Одним сообщением два вызова Agent: `subagent_type: review-standards` и `subagent_type: review-conformance`. |
| pi | Два отдельных процесса `devflow agent run`, по возможности параллельно; команды ниже. Не вызывай Claude. |

В отдельном временном каталоге создай `standards.in.md` и `conformance.in.md`.
Каждый содержит только cwd, базу/HEAD, точную цель, слаг и «сделай свою ось и верни находки».
Не передавай историю разговора, собственные находки или результат другой оси.

```bash
devflow agent run review-standards --message-file <tmp>/standards.in.md > <tmp>/standards.out.json &
devflow agent run review-conformance --message-file <tmp>/conformance.in.md > <tmp>/conformance.out.json &
wait
```

Прочитай оба JSON отдельно: `exit_code`, `warning`, `report`. Ошибка процесса, пустой ответ
или предупреждение означают незавершённую ось, а не отсутствие замечаний.
Последовательный запуск допустим, но второй вход остаётся исходным: чужие находки не добавлять.
Логика проверки живёт в телах агентов — не пересказывай её здесь.

Есть `<vault>/tz/<slug>.md`? Проверять заранее не нужно: ось соответствия сама вернёт
`ТЗ не найдено`, и это её законный ответ.

## Step 3: Показать два раздела
```
## Стандарты
<находки оси 1, худшее первым — как вернул агент>

## Соответствие ТЗ
<находки оси 2, худшее первым — как вернул агент>
```

Правила вывода:
- **Не сливать и не переранжировать.** Находка оси не переезжает в чужой раздел и не сравнивается
  с чужой по важности. Итог называет худшее *внутри каждой* оси.
- **Не сокращать цитаты ТЗ** — они и делают находку проверяемой.
- Ось соответствия вернула `ТЗ не найдено` → так и написать в её разделе: «ТЗ не найдено — ось
  соответствия пропущена». Пустого раздела быть не должно.
- Обе оси чисты → сказать это двумя строками, по одной на ось.

## Step 4: Что дальше
Кончай рекомендацией, а не правкой: что чинить в первую очередь по каждой оси. Правки — отдельный
заход; этот скилл ничего не меняет.

## Rules
- **Только чтение репозитория.** Ни правок, ни коммитов; служебные входы/выходы — вне репозитория.
  До и после сними `git status --porcelain=v1 --untracked-files=all` и `git diff HEAD --binary`,
  сравни также содержимое untracked-файлов. Изменение дерева — нарушение, не откатывай чужие правки.
  Роли не получают Write/Edit; действует политика инструментов. Доступ к Bash не является изоляцией ОС.
- **Две оси — два контекста.** Никогда не запускай их в одном агенте «для экономии»: смешанный
  контекст ровно та ошибка, ради которой оси разведены.
- **ТЗ не подменяется.** Ни research, ни план, ни описание в Jira не годятся как контракт.
